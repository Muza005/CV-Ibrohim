RBAC for Node.js APIs: roles, permissions and middleware that scale

Nov 2026|5 min read|Security

RBACauthorize('ticket:update')

Authentication answers who is calling. Authorization answers what they are allowed to do, and that second question is where most API security problems hide. At Telecom Soft I implemented role-based access control (RBAC) to strengthen API security, access control and data protection, and I have since used the same approach in M-System and in a B2B ticketing module.

Here is the model I use, the Express middleware that enforces it and the details that make it hold up in production.

Roles describe people, permissions describe actions

The core idea of RBAC is one level of indirection. Instead of checking “is this user an admin?” all over the codebase, you check for a permission, and roles are simply named bundles of permissions.

  • A permission is an action on a resource: ticket:read, ticket:update, project:delete, report:read-all.
  • A role groups permissions: viewer, member, manager, admin.
  • A user has one or more roles.

The code only ever asks for permissions. Roles can change, be split or be renamed without touching a single route.

The schema

Three entities and two join tables are enough:

sql
CREATE TABLE roles (
  id   SERIAL PRIMARY KEY,
  name VARCHAR(50) UNIQUE NOT NULL
);

CREATE TABLE permissions (
  id   SERIAL PRIMARY KEY,
  name VARCHAR(100) UNIQUE NOT NULL   -- e.g. 'ticket:update'
);

CREATE TABLE role_permissions (
  role_id       INT REFERENCES roles(id) ON DELETE CASCADE,
  permission_id INT REFERENCES permissions(id) ON DELETE CASCADE,
  PRIMARY KEY (role_id, permission_id)
);

CREATE TABLE user_roles (
  user_id INT REFERENCES users(id) ON DELETE CASCADE,
  role_id INT REFERENCES roles(id) ON DELETE CASCADE,
  PRIMARY KEY (user_id, role_id)
);

In Sequelize these become many-to-many associations (with underscored: true, so the foreign keys match the snake_case columns):

js
// models/index.js
User.belongsToMany(Role, { through: 'user_roles', as: 'roles' });
Role.belongsToMany(User, { through: 'user_roles', as: 'users' });
Role.belongsToMany(Permission, { through: 'role_permissions', as: 'permissions' });

Loading permissions, with a Redis cache

Permissions are read on almost every request, so they are a perfect candidate for caching. I load the flattened permission names for a user once, keep them in Redis for a few minutes and invalidate the key when that user’s roles change.

js
// rbac/permissions.js
import { redis } from '../lib/redis.js';        // ioredis client
import { Role, Permission } from '../models/index.js';

const TTL_SECONDS = 300;

export async function getPermissions(userId) {
  const key = `perms:${userId}`;
  const cached = await redis.get(key);
  if (cached) return new Set(JSON.parse(cached));

  const roles = await Role.findAll({
    include: [
      { association: 'users', where: { id: userId }, attributes: [] },
      { model: Permission, as: 'permissions', attributes: ['name'], through: { attributes: [] } },
    ],
  });

  const names = [...new Set(roles.flatMap((role) => role.permissions.map((p) => p.name)))];
  await redis.set(key, JSON.stringify(names), 'EX', TTL_SECONDS);
  return new Set(names);
}

export const invalidatePermissions = (userId) => redis.del(`perms:${userId}`);

The middleware

authorize() runs after authenticate() has verified the JWT and attached req.user. It is small on purpose:

js
// middleware/authorize.js
import { getPermissions } from '../rbac/permissions.js';

export function authorize(...required) {
  return async (req, res, next) => {
    try {
      if (!req.user) {
        return res.status(401).json({ error: 'UNAUTHENTICATED' });
      }

      const granted = await getPermissions(req.user.id);
      const missing = required.filter((permission) => !granted.has(permission));

      if (missing.length > 0) {
        req.log?.warn({ userId: req.user.id, missing }, 'rbac: access denied');
        return res.status(403).json({ error: 'FORBIDDEN' });
      }

      return next();
    } catch (err) {
      return next(err);
    }
  };
}

Using it reads almost like documentation:

js
router.get('/tickets', authenticate, authorize('ticket:read'), ticketController.list);
router.patch('/tickets/:id/status', authenticate, authorize('ticket:update'), ticketController.changeStatus);
router.delete('/projects/:id', authenticate, authorize('project:delete'), projectController.remove);

Notice that the response for a denied request does not list which permissions were missing. That detail goes to the logs, not to the client.

Roles are not enough: scope every query

RBAC says a support agent may read tickets. It does not say which tickets. In a B2B system the answer is “only those of their own organization”, and that check belongs in the data access layer, not in the controller:

js
// tickets/ticket.service.js
export async function getTicket(id, actor) {
  const ticket = await Ticket.findOne({
    where: { id, organizationId: actor.organizationId },
  });

  // 404, not 403: don't confirm that another organization's ticket exists
  if (!ticket) throw new NotFoundError('Ticket not found');
  return ticket;
}

If the scope lives in the query, a forgotten check cannot leak another customer’s data, because the row is never loaded in the first place.

Make the permission matrix visible

A table in the documentation prevents most arguments about “who should be able to do what”:

Permission Viewer Member Manager Admin
project:read ✓ ✓ ✓ ✓
task:update ✓ ✓ ✓
report:read-all ✓ ✓
project:delete ✓

The same matrix drives the seed data and a test that calls each protected endpoint with each role and expects 2xx or 403. When someone changes a role, the test shows exactly what changed.

A short checklist

  1. Deny by default. A route without authorize() should fail review.
  2. Check on the server. Hiding a button in the UI is a convenience, not security.
  3. Scope every query to the user’s organization or project.
  4. Return 404 for out-of-scope resources so IDs cannot be probed.
  5. Cache permissions, and invalidate on role changes.
  6. Log denials with the user and the missing permission. A burst of 403s is often the first sign of a bug or of someone probing your API.
  7. Keep roles few and permissions many. Fine-grained permissions are cheap; a new role for every exception is not.

RBAC is not glamorous, but it is one of the highest-leverage things you can build into a backend. Once it is in place, every new endpoint is secure by default instead of secure by memory.
