Spec-driven API development with OpenAPI and Swagger

Nov 2026|4 min read|API design

OpenAPIcontract first, code second

Most API bugs I have seen were not coding mistakes. They were misunderstandings: the frontend expected status, the backend returned state; QA tested a flow nobody had agreed on; an error case simply had no defined response. Spec-driven development attacks that problem at the source. The team agrees on the contract first, and the code is written to satisfy it.

I use Swagger/OpenAPI for API documentation and apply spec-driven design to capture system requirements and development workflows. Here is what that looks like in practice.

What “spec-driven” means day to day

  1. Write down the behaviour in plain language: who calls the endpoint, what they send, what can go wrong.
  2. Turn it into an OpenAPI description: paths, parameters, request bodies, responses and errors.
  3. Review the spec with frontend, QA and whoever owns the business process. Changing YAML is cheap; changing a released API is not.
  4. Implement against the spec, reusing its schemas for request validation.
  5. Publish the docs with Swagger UI, generated from the same source, so they cannot drift away from the code.

The frontend can start building against the agreed contract on day one, while the backend is still being written.

A small contract

Here is a trimmed example from a B2B ticketing module: changing the status of a support ticket.

yaml
openapi: 3.0.3
info:
  title: B2B Tickets API
  version: 1.0.0
paths:
  /tickets/{id}/status:
    patch:
      summary: Change the status of a ticket
      tags: [tickets]
      security:
        - bearerAuth: []
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: integer }
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [status]
              additionalProperties: false
              properties:
                status:
                  type: string
                  enum: [open, in_review, resolved, rejected]
                comment:
                  type: string
                  maxLength: 1000
      responses:
        '200': { description: Ticket updated }
        '403': { description: Not allowed for this role }
        '404': { description: Ticket not found in your organization }
        '409': { description: Transition not allowed from the current status }
components:
  securitySchemes:
    bearerAuth: { type: http, scheme: bearer, bearerFormat: JWT }

Even this small piece answers questions that usually come up only during testing. Which statuses exist? Is a comment required? What happens when the transition is not allowed? The answer is a 409, and everyone knows it before a line of code exists.

One schema, two jobs: validation and docs

Fastify uses JSON Schema for validation and serialization, and @fastify/swagger turns the same route schemas into an OpenAPI document. Describing the route once gives you input validation, faster response serialization and documentation:

js
import Fastify from 'fastify';
import swagger from '@fastify/swagger';
import swaggerUi from '@fastify/swagger-ui';

const app = Fastify({ logger: true });

await app.register(swagger, {
  openapi: {
    info: { title: 'B2B Tickets API', version: '1.0.0' },
    components: {
      securitySchemes: { bearerAuth: { type: 'http', scheme: 'bearer', bearerFormat: 'JWT' } },
    },
  },
});
await app.register(swaggerUi, { routePrefix: '/docs' });

app.addSchema({
  $id: 'Error',
  type: 'object',
  required: ['error', 'message'],
  properties: {
    error: { type: 'string' },
    message: { type: 'string' },
  },
});

app.patch('/tickets/:id/status', {
  schema: {
    tags: ['tickets'],
    summary: 'Change the status of a ticket',
    security: [{ bearerAuth: [] }],
    params: {
      type: 'object',
      required: ['id'],
      properties: { id: { type: 'integer' } },
    },
    body: {
      type: 'object',
      required: ['status'],
      additionalProperties: false,
      properties: {
        status: { type: 'string', enum: ['open', 'in_review', 'resolved', 'rejected'] },
        comment: { type: 'string', maxLength: 1000 },
      },
    },
    response: {
      200: {
        type: 'object',
        properties: { id: { type: 'integer' }, status: { type: 'string' } },
      },
      409: { $ref: 'Error#' },
    },
  },
  preHandler: [authenticate, authorize('ticket:update')],
}, changeStatusHandler);

A request with an unknown status never reaches the handler; Fastify rejects it with a 400 and a precise message. The response schema also acts as a safety net, because properties that are not in it are not serialized, so an internal field cannot leak by accident.

Agree on errors, not just on success

The happy path is the easy part of a contract. I define one error shape for the whole API and document every error status per endpoint:

json
{
  "error": "INVALID_TRANSITION",
  "message": "A ticket cannot move from \"resolved\" to \"in_review\"",
  "details": { "from": "resolved", "to": "in_review" }
}

error is a stable, machine-readable code that the frontend can switch on. message is for humans and can change. details is optional context. With this shape, clients need one error handler, not twenty.

Keeping the spec honest

A spec that drifts away from the code is worse than no spec at all. These habits keep it accurate:

  • Generate the docs from the code (route schemas) or validate the code against the spec. Never maintain both by hand.
  • Review spec changes like code changes. A pull request that changes a response shape should show it in the diff.
  • Version breaking changes (/v1, /v2) and add fields instead of renaming them.
  • Document examples for both success and errors. Examples are what developers copy first.

Why it is worth it

Spec-driven development feels slower for the first hour and much faster for the rest of the project. Frontend and backend work in parallel, QA writes test cases from the contract, and onboarding a new developer starts with reading /docs instead of reverse-engineering controllers. As a bonus, a precise spec is excellent context for AI coding assistants, which I wrote about in How I use AI agents in my backend workflow.
