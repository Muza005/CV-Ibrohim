Status history and audit logs with PostgreSQL and Sequelize

Nov 2026|5 min read|Databases

SQLticket_status_history

In a B2B support system, the question that matters most is rarely “what is the status of this ticket?”. It is “who changed it, when, and why?”. A client wants to know why their appeal was rejected; a manager wants to know how long tickets sit in review; an auditor wants proof. When I built a modular backend for B2B complaints, appeals and support tickets, status history and audit logging were first-class parts of the data model, not afterthoughts.

Here is the design I use, shown with PostgreSQL and Sequelize.

Three tables, three jobs

  • tickets holds the current state, fast to read and easy to filter.
  • ticket_status_history is an append-only timeline of status changes for each ticket.
  • audit_logs is a generic, append-only record of significant actions across the whole system.
sql
CREATE TABLE tickets (
  id              BIGSERIAL PRIMARY KEY,
  organization_id BIGINT       NOT NULL REFERENCES organizations(id),
  subject         VARCHAR(200) NOT NULL,
  status          VARCHAR(32)  NOT NULL DEFAULT 'open',
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE ticket_status_history (
  id            BIGSERIAL PRIMARY KEY,
  ticket_id     BIGINT      NOT NULL REFERENCES tickets(id) ON DELETE CASCADE,
  from_status   VARCHAR(32),               -- NULL for the first entry
  to_status     VARCHAR(32) NOT NULL,
  changed_by_id BIGINT      NOT NULL REFERENCES users(id),
  comment       TEXT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE audit_logs (
  id          BIGSERIAL PRIMARY KEY,
  actor_id    BIGINT REFERENCES users(id),
  action      VARCHAR(64) NOT NULL,        -- e.g. 'ticket.status_changed'
  entity_type VARCHAR(32) NOT NULL,
  entity_id   BIGINT      NOT NULL,
  metadata    JSONB       NOT NULL DEFAULT '{}',
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

Why not just one table? Because they answer different questions. The history table is optimized for “show me this ticket’s timeline”. The audit log is optimized for “show me everything this user did last week” or “everything that happened to entity X”, across many entity types.

The Sequelize side

js
const TicketStatusHistory = sequelize.define('TicketStatusHistory', {
  fromStatus: { type: DataTypes.STRING(32), allowNull: true },
  toStatus: { type: DataTypes.STRING(32), allowNull: false },
  comment: { type: DataTypes.TEXT },
}, {
  tableName: 'ticket_status_history',
  underscored: true,
  updatedAt: false,          // history rows are never updated
});

Ticket.hasMany(TicketStatusHistory, { as: 'history', foreignKey: 'ticketId' });
TicketStatusHistory.belongsTo(User, { as: 'changedBy', foreignKey: 'changedById' });

updatedAt: false is a small but honest signal: these rows are facts about the past, and nobody should be editing them.

Changing a status: rules, a transaction and a lock

Allowed transitions are explicit. Every status change writes three things, and they must succeed or fail together, so they share one transaction:

js
const TRANSITIONS = {
  open: ['in_review', 'rejected'],
  in_review: ['resolved', 'rejected', 'open'],
  rejected: ['open'],
  resolved: [],
};

export async function changeStatus({ ticketId, toStatus, comment, actor }) {
  return sequelize.transaction(async (t) => {
    // Lock the row so two agents can't change the same ticket at the same time
    const ticket = await Ticket.findOne({
      where: { id: ticketId, organizationId: actor.organizationId },
      lock: t.LOCK.UPDATE,
      transaction: t,
    });
    if (!ticket) throw new NotFoundError('Ticket not found');

    const fromStatus = ticket.status;
    if (!TRANSITIONS[fromStatus]?.includes(toStatus)) {
      throw new ConflictError(`A ticket cannot move from "${fromStatus}" to "${toStatus}"`);
    }

    await ticket.update({ status: toStatus }, { transaction: t });

    await TicketStatusHistory.create(
      { ticketId, fromStatus, toStatus, comment, changedById: actor.id },
      { transaction: t },
    );

    await AuditLog.create({
      actorId: actor.id,
      action: 'ticket.status_changed',
      entityType: 'ticket',
      entityId: ticketId,
      metadata: { fromStatus, toStatus },
    }, { transaction: t });

    return ticket;
  });
}

Three details carry most of the weight here:

  • SELECT … FOR UPDATE (lock: t.LOCK.UPDATE) prevents two concurrent requests from both reading open and both writing a transition.
  • The organization filter in the query makes the change impossible for users outside the ticket’s organization; they get a 404.
  • One transaction means there is never a status without its history row, or a history row without its audit entry.

Reading the timeline

With the association in place, the timeline is a single query:

js
const timeline = await TicketStatusHistory.findAll({
  where: { ticketId },
  order: [['createdAt', 'ASC']],
  include: [{ association: 'changedBy', attributes: ['id', 'fullName'] }],
});

The same data powers simple analytics. For example, here is the average time from the first in_review to resolved:

sql
SELECT avg(t.resolved_at - t.review_at) AS avg_review_time
FROM (
  SELECT ticket_id,
         min(created_at) FILTER (WHERE to_status = 'in_review') AS review_at,
         max(created_at) FILTER (WHERE to_status = 'resolved')  AS resolved_at
  FROM ticket_status_history
  GROUP BY ticket_id
) AS t
WHERE t.review_at IS NOT NULL
  AND t.resolved_at IS NOT NULL;

Indexes that match the questions

sql
CREATE INDEX idx_tsh_ticket_created ON ticket_status_history (ticket_id, created_at);
CREATE INDEX idx_audit_entity      ON audit_logs (entity_type, entity_id, created_at DESC);
CREATE INDEX idx_audit_actor       ON audit_logs (actor_id, created_at DESC);

Each index matches a real screen or report: the ticket timeline, the history of one entity and the activity of one user.

Why not database triggers?

Triggers can record every change automatically, which is tempting. Their weakness is context: a trigger sees the row, but not the user, the reason or the request that caused the change. Recording history in the service layer keeps the actor and the comment in the same transaction. When you need a safety net for changes made outside the application, a trigger-based audit can sit alongside it.

Rules of thumb

  1. Append-only. History and audit rows are inserted, never updated or deleted by the application.
  2. Store the actor and the reason, not only the new value.
  3. Keep metadata in JSONB so new event types don’t require migrations.
  4. Write history in the same transaction as the change it describes.
  5. Plan retention early. Audit tables grow forever unless you decide otherwise.

The payoff is a system that can always explain itself, and that is worth far more to a support team than a few saved inserts.
