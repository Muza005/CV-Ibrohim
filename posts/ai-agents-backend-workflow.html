How I use AI agents in my backend workflow

Nov 2026|4 min read|AI & tooling

AI agentshumans decide · agents assist

AI agents have quickly become part of how software gets built. I have been steadily expanding my practical knowledge of AI agents and agentic AI: how they fit into software development, automation, documentation and everyday engineering workflows. I have also integrated AI-agentic capabilities into a production system (M-System).

This post is not about hype. It is about where agents genuinely save me time as a backend developer, and the rules I keep so that speed never costs correctness or security.

Where agents help the most

Research and orientation. Reading the documentation of a library I have not used before, comparing two approaches or explaining an unfamiliar error. An agent is a fast first pass. I still confirm the important parts in the official docs.

Drafting specs and docs. Turning my notes from a requirements discussion into a first draft of an OpenAPI path, a README section or a short design document. Editing a draft is much faster than starting from a blank page.

Scaffolding the predictable parts. Route boilerplate, request validation schemas, Sequelize migrations, seed data and the skeleton of a test file. This is code I could write with my eyes closed, so it is the safest place to delegate.

Finding the edge cases. Asking “what inputs would break this function?” or “list the failure modes of this OTP flow” regularly surfaces cases worth a test: an expired challenge, a repeated request, a missing header.

Reviewing my own diff. Before opening a pull request, a second look at the change often catches an unhandled error path, an N+1 query or a forgotten await.

Reading logs. Summarizing a wall of structured logs into “these three requests failed for the same reason” is a surprisingly good use of an agent.

The guardrails I keep

  1. I own every decision. An agent can propose; I decide. If I cannot explain a line of code, it does not get merged.
  2. No secrets, no customer data. API keys, tokens, real personal data and internal credentials never go into a prompt.
  3. Everything goes through the normal pipeline. Tests, linting and code review apply to generated code exactly as they apply to mine.
  4. Small, well-scoped tasks. “Write the validation schema for this endpoint” works far better than “build the module”.
  5. Give it the contract. A precise spec is the best context an agent can get. This is one more reason I like spec-driven API development: the same OpenAPI document guides people and tools.

Agentic features inside a product

Using agents as a developer is one thing; letting an agent act inside your product is another. When I add AI-agentic capabilities to a backend, the agent is treated as just another API client, with the same rules as a person:

  • Same permissions as the user. The agent acts on behalf of the person who invoked it, through the same endpoints and the same RBAC checks. It never gets a privileged back door.
  • Narrow, typed tools. Each capability the agent can call is a small, documented operation with a strict input schema, not “run any query”.
  • Everything is logged. Agent actions go to the audit log with the user who triggered them.
  • A human confirms anything destructive. Reading and suggesting are automatic; deleting or bulk-changing data needs a click from a person.
  • Limits. Rate limits and timeouts apply to agent calls exactly as to any other client.

A tool definition can be as simple as an existing endpoint described with a JSON Schema:

json
{
  "name": "list_overdue_tasks",
  "description": "List overdue tasks in a project the current user can access.",
  "input_schema": {
    "type": "object",
    "required": ["projectId"],
    "additionalProperties": false,
    "properties": {
      "projectId": { "type": "integer" },
      "limit": { "type": "integer", "minimum": 1, "maximum": 50, "default": 20 }
    }
  }
}

Behind that definition sits a normal, authorized API call, so the agent can only see what the user could already see.

What has changed for me

The biggest change is not that I type less code. It is that I spend more of my time on the parts that need a human: understanding the business process, designing the data model, choosing trade-offs and reviewing the result. The boring parts got faster, and the important parts got more attention.

If you are a backend developer who has not tried working with agents yet, start small: let one draft the tests for a function you just wrote, then review them as carefully as you would review a colleague’s work.
