OTP two-step verification with Fastify and Redis

Nov 2026|5 min read|Security

2FASET 2fa:{id} … EX 120

A password alone is a single point of failure. Two-step verification adds a second factor, and an SMS one-time password (OTP) is still the most familiar one for many users. I built an OTP-based 2FA flow with Node.js, Fastify and Redis, and the interesting part was not sending a code. It was everything around it: expiry, retry and resend limits, rate limiting, device validation and making sure a session is created only after successful verification.

The flow

  1. The user submits their credentials. If they are valid, no session is created yet.
  2. The API creates a short-lived challenge in Redis and sends a 6-digit code through an external SMS provider.
  3. The client shows a code screen and sends the code together with the challenge ID.
  4. If the code is correct, the challenge is consumed and only then is a session issued.

Everything between steps 1 and 4 is temporary authentication state, which is exactly what Redis is good at: fast reads, atomic operations and automatic expiry.

What lives in Redis

txt
2fa:{challengeId}            JSON, expires after 120 seconds
  userId     who is logging in
  otpHash    HMAC of the code (never the code itself)
  attempts   wrong codes so far
  resends    codes sent again so far
  deviceId   the device that started the login

2fa:cooldown:{challengeId}   exists for 30 seconds after each send

Storing a hash means that even someone with read access to Redis cannot log in as a user. The TTL means that abandoned logins clean themselves up.

Step 1: login creates a challenge

js
import crypto from 'node:crypto';

const OTP_TTL = 120;      // seconds a code stays valid
const MAX_ATTEMPTS = 5;   // wrong codes per challenge
const MAX_RESENDS = 3;    // extra codes per challenge
const COOLDOWN = 30;      // seconds between sends

const hashOtp = (challengeId, code) =>
  crypto.createHmac('sha256', process.env.OTP_SECRET).update(`${challengeId}:${code}`).digest('hex');

const newCode = () => crypto.randomInt(0, 1_000_000).toString().padStart(6, '0');

app.post('/auth/login', {
  schema: loginSchema,
  config: { rateLimit: { max: 5, timeWindow: '1 minute' } },
}, async (req, reply) => {
  const user = await verifyCredentials(req.body.phone, req.body.password);
  if (!user) return reply.code(401).send({ error: 'INVALID_CREDENTIALS' });

  const challengeId = crypto.randomUUID();
  const code = newCode();
  const state = {
    userId: user.id,
    otpHash: hashOtp(challengeId, code),
    attempts: 0,
    resends: 0,
    deviceId: req.headers['x-device-id'],
  };

  await app.redis.set(`2fa:${challengeId}`, JSON.stringify(state), 'EX', OTP_TTL);
  await app.redis.set(`2fa:cooldown:${challengeId}`, '1', 'EX', COOLDOWN);
  await sms.send(user.phone, `Your verification code: ${code}`);

  return reply.code(202).send({ challengeId, expiresIn: OTP_TTL });
});

crypto.randomInt uses a cryptographically secure generator. Math.random() does not belong anywhere near authentication.

Step 2: verification, consumed exactly once

js
app.post('/auth/otp/verify', {
  schema: verifySchema,
  config: { rateLimit: { max: 10, timeWindow: '1 minute' } },
}, async (req, reply) => {
  const { challengeId, code } = req.body;
  const key = `2fa:${challengeId}`;

  const raw = await app.redis.get(key);
  if (!raw) return reply.code(410).send({ error: 'CHALLENGE_EXPIRED' });

  const state = JSON.parse(raw);
  if (state.deviceId !== req.headers['x-device-id']) {
    return reply.code(403).send({ error: 'DEVICE_MISMATCH' });
  }

  const expected = Buffer.from(state.otpHash, 'hex');
  const actual = Buffer.from(hashOtp(challengeId, code), 'hex');

  if (!crypto.timingSafeEqual(expected, actual)) {
    state.attempts += 1;
    if (state.attempts >= MAX_ATTEMPTS) {
      await app.redis.del(key);
      return reply.code(429).send({ error: 'TOO_MANY_ATTEMPTS' });
    }
    await app.redis.set(key, JSON.stringify(state), 'KEEPTTL');
    return reply.code(401).send({ error: 'INVALID_CODE', attemptsLeft: MAX_ATTEMPTS - state.attempts });
  }

  // DEL returns 1 for exactly one caller, so two parallel requests can't both win
  const consumed = await app.redis.del(key);
  if (consumed !== 1) return reply.code(410).send({ error: 'CHALLENGE_EXPIRED' });

  const session = await createSession(state.userId, state.deviceId);
  return reply.send(session);
});

A few details worth calling out:

  • timingSafeEqual compares the hashes in constant time. Both buffers are SHA-256 digests, so their lengths always match.
  • KEEPTTL (Redis 6+) updates the attempt counter without extending the code’s lifetime.
  • Consuming with DEL makes the success path atomic: if two requests arrive with the right code at the same moment, only one of them gets 1 back and creates a session.
  • Under heavy traffic, the attempt counter can be stored in a Redis hash and incremented with HINCRBY, so concurrent wrong guesses can’t overwrite each other’s updates. Rate limiting keeps that window small either way.

Step 3: resending, without turning the API into an SMS cannon

js
app.post('/auth/otp/resend', { schema: resendSchema }, async (req, reply) => {
  const { challengeId } = req.body;
  const key = `2fa:${challengeId}`;

  // NX: only succeeds if the cooldown key does not exist yet
  const allowed = await app.redis.set(`2fa:cooldown:${challengeId}`, '1', 'EX', COOLDOWN, 'NX');
  if (!allowed) return reply.code(429).send({ error: 'RESEND_TOO_SOON', retryAfter: COOLDOWN });

  const raw = await app.redis.get(key);
  if (!raw) return reply.code(410).send({ error: 'CHALLENGE_EXPIRED' });

  const state = JSON.parse(raw);
  if (state.resends >= MAX_RESENDS) return reply.code(429).send({ error: 'TOO_MANY_RESENDS' });

  const code = newCode();
  Object.assign(state, { otpHash: hashOtp(challengeId, code), attempts: 0, resends: state.resends + 1 });
  await app.redis.set(key, JSON.stringify(state), 'EX', OTP_TTL);

  const user = await User.findByPk(state.userId, { attributes: ['phone'] });
  await sms.send(user.phone, `Your verification code: ${code}`);
  return reply.code(202).send({ expiresIn: OTP_TTL });
});

SMS costs money and SMS pumping is a real attack, so the cooldown and the resend limit protect the budget as much as the user.

Rate limiting in front of everything

Per-challenge limits are not enough on their own: an attacker can simply start new challenges. Route-level rate limits with @fastify/rate-limit, backed by the same Redis, cap how often a client can hit the login and OTP endpoints:

js
await app.register(import('@fastify/rate-limit'), {
  global: false,        // opt in per route through `config.rateLimit`
  redis: app.redis,     // shared counters across all API instances
});

Lessons learned

  1. Never store or log the code. Store an HMAC; log events such as “otp sent” or “otp failed”, not values.
  2. Keep error messages useful but boring. Tell the user that the code is wrong or expired; don’t reveal whether the account exists.
  3. Make the success path atomic. One code, one session.
  4. Short TTLs are a feature. Two minutes is enough for a human and too short for most automated attacks.
  5. Treat the SMS provider as unreliable. Time out, retry carefully and give the user a clear way to request a new code.

Done well, a second factor feels like a small extra step for the user and a wall for everyone else.
