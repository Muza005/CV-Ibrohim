Building M-System: an internal alternative to Notion for our team

Nov 2026|5 min read|Case studies

M-Systemprojects · tasks · daily reports

M-System is an internal platform I designed and built at Telecom Soft for projects, tasks and daily reports. It started as “a lightweight alternative to Notion for our team” and became the place where work is planned, tracked and reported. It runs in production, uses role-based access control for every action, includes AI-agentic features, and contributed to an estimated 20% improvement in team workflow efficiency.

This post is a tour of the decisions behind it: what we needed, how the backend is structured and what I would do the same way again.

Why build an internal tool at all?

General-purpose workspaces are flexible, and that flexibility has a cost. Every team invents its own structure, permissions are coarse, and turning scattered notes into a report means copying data around by hand.

What we needed was narrower and stricter:

  • Projects with members, and roles that decide what each member can see and do.
  • Tasks with assignees, deadlines and a status that follows a defined workflow.
  • Daily reports, so progress is visible without extra meetings.
  • Access rules that match the organization, enforced by the backend rather than by convention.
  • Data that lives in our own PostgreSQL database, ready for reporting and integrations.

Architecture at a glance

The system is deliberately boring in the best sense of the word: a React client, Nginx in front, an Express.js API, PostgreSQL as the source of truth and Redis for caching and short-lived state.

txt
React client ──▶ Nginx ──▶ Express API ──▶ PostgreSQL (Sequelize)
                               │    └────▶ Redis (cache, short-lived state)
                               └─────────▶ AI agent (same permissions as the user)

Inside the API, every feature is an independently structured module with the same layers. A new developer can open any folder and know where to look:

txt
src/
  modules/
    auth/        routes · controller · service · validation
    projects/    routes · controller · service · model
    tasks/       routes · controller · service · model
    reports/     routes · controller · service · model
  middleware/    authenticate · authorize · validate · errorHandler
  lib/           db · redis · logger

Routes stay thin, controllers translate HTTP into function calls, services hold the business rules, and models describe data. Nothing in a service knows about req or res, which keeps the rules easy to test and to reuse from background jobs.

The data model

A simplified version of the core model looks like this. Most of the important rules are visible in the relationships alone:

js
// models/index.js (simplified)
User.belongsToMany(Role, { through: 'user_roles', as: 'roles' });
Role.belongsToMany(Permission, { through: 'role_permissions', as: 'permissions' });

Project.belongsToMany(User, { through: ProjectMember, as: 'members' });
Project.hasMany(Task, { as: 'tasks', foreignKey: 'projectId' });

Task.belongsTo(User, { as: 'assignee', foreignKey: 'assigneeId' });
Task.hasMany(TaskStatusHistory, { as: 'history', foreignKey: 'taskId' });

User.hasMany(DailyReport, { as: 'reports', foreignKey: 'userId' });

Two choices paid off early. First, membership is a real model (ProjectMember) instead of a plain join table, so it can carry a role inside the project. Second, status changes are stored as history rows, not only as the current value, so “when did this task move to review?” is a query, not a guess.

RBAC on every endpoint

Permissions are named resource:action (task:update, report:read-all) and checked by one middleware before a controller runs. The rule is deny by default: if a route has no explicit permission, it is not reachable.

js
router.patch(
  '/projects/:projectId/tasks/:taskId',
  authenticate,
  authorize('task:update'),
  validate(updateTaskSchema),
  taskController.update,
);

The permission tells us what a user may do; the service still checks where, so a member of one project cannot touch another project’s tasks by guessing IDs. I wrote about the full approach in RBAC for Node.js APIs.

Workflows as rules, not conventions

A task should not jump from “todo” straight to “done” because someone clicked the wrong button. In a simplified form, the allowed transitions live in one place and the service refuses anything else:

js
const TRANSITIONS = {
  todo: ['in_progress'],
  in_progress: ['review', 'todo'],
  review: ['done', 'in_progress'],
  done: [],
};

export function assertTransition(from, to) {
  if (!TRANSITIONS[from]?.includes(to)) {
    throw new ConflictError(`A task cannot move from "${from}" to "${to}"`);
  }
}

Keeping the workflow explicit made it easy to discuss with the team: the rules are readable by people who never open the code.

Let the database enforce simple rules

Some rules are simple enough for PostgreSQL to guarantee. “One daily report per person per day”, for example, is a unique constraint rather than a check that lives only in the UI:

sql
ALTER TABLE daily_reports
  ADD CONSTRAINT daily_reports_one_per_day UNIQUE (user_id, report_date);

The API turns a violation into a clear 409 Conflict, and the client can offer to edit the existing report instead.

AI-agentic capabilities, with guardrails

The most interesting part of M-System is its AI-agentic capabilities, which help people work with their own projects and tasks. The guardrails I follow matter more than the model:

  • The agent acts with the permissions of the user who invoked it, through the same API and the same authorize() checks.
  • Every action it takes is logged, just like a human action.
  • Anything destructive needs a human confirmation.

An agent that can bypass access control is a security incident waiting to happen. An agent that is just another API client is a feature.

Shipping it

The API runs on Linux behind Nginx, which sits in front as a reverse proxy. Redis takes care of caching and short-lived state, and structured logs make it easy to see what happened when someone reports a problem.

What I learned

  1. Start from workflows, not screens. The status transitions and permissions shaped the data model, and the UI followed.
  2. Put access control in the data model early. Retrofitting RBAC onto existing endpoints is far harder than designing for it.
  3. Keep modules independent. When a module owns its routes, rules and models, changes stay local.
  4. Write the docs while you build. The Swagger spec and short design notes made onboarding and frontend work much faster.

M-System is not the most complex system I have worked on, but it is the one that taught me the most about building software that people use every day.
